# Server-Side Adaptation Specification

## Summary
Implement server-side adaptations to support client‑side VAD segments, provide a fallback VAD processing path, optimize audio handling, and add monitoring/logging. This ensures robust speech processing even when client‑side VAD is unavailable or disabled.

## Goals
- Enable LitServe to accept chunked audio segments generated by client‑side VAD.
- Provide a server‑side VAD fallback that mimics client behavior when needed.
- Optimize audio conversion and validation to reduce latency.
- Deliver consistent JSON response format with performance metrics.
- Add usage tracking and error logging for observability.

## Actors
- **Client Browser**: Sends speech segments via HTTP POST.
- **LitServe Server**: Processes incoming audio, runs VAD (client or server), STT, LLM, TTS.
- **Operations Team**: Monitors metrics and logs.

## User Scenarios & Testing
1. **Normal Flow**: Client VAD detects speech, sends segmented audio. Server reassembles, runs STT, returns transcription.
2. **Fallback Flow**: Client disables VAD or fails detection. Server performs VAD on full audio stream and returns result.
3. **Error Handling**: Corrupted audio chunk received – server returns a clear error response and logs the incident.
4. **Monitoring**: Operations view dashboards showing VAD usage percentages, processing latency, and error rates.

## Functional Requirements
- FR1: Accept HTTP POST requests at `/api/vad/segments` containing chunked PCM audio with metadata (sequence, timestamps).
- FR2: Reassemble chunks into complete utterances based on sequence numbers.
- FR3: Detect when client VAD is unavailable (missing metadata flag) and invoke server‑side VAD fallback.
- FR4: Perform VAD using existing Silero model and produce speech start/end timestamps.
- FR5: Pass processed audio to STT pipeline and return transcription in JSON.
- FR6: Include processing latency, VAD mode (client/server), and any error codes in the response.
- FR7: Log each request with request ID, VAD mode, processing time, and success/failure status.
- FR8: Emit metrics for VAD usage (percentage client vs server), average latency, and error rate.

## Non‑Functional Requirements
- NFR1: End‑to‑end latency for a typical utterance must be ≤ 500 ms.
- NFR2: Server‑side VAD fallback must not increase CPU usage beyond 20 % above baseline.
- NFR3: Error responses must be returned within 200 ms.
- NFR4: All logging must comply with GDPR‑compatible anonymization.

## Assumptions
- Clients will include an `X-Client-VAD` header with values `true` (VAD enabled) or `false` (VAD disabled).
- Audio is PCM 16‑bit, 16 kHz, mono.
- Existing Silero VAD model is already loaded and can be reused for fallback.
- Monitoring stack (Prometheus + Grafana) is available in the deployment environment.

## Success Criteria
- 95 % of speech segments are processed with total latency ≤ 500 ms.
- Server‑side VAD fallback is triggered in <5 % of real‑world sessions.
- Monitoring dashboard shows error rate < 0.5 % per day.
- No regression in transcription accuracy compared to Phase 1 baseline.

## Key Entities
- **AudioChunk**: sequence number, timestamp, base64 PCM data.
- **Utterance**: collection of AudioChunks forming a complete speech segment.
- **VADResult**: start/end timestamps, confidence, mode (client/server).
- **Metrics**: processing time, VAD mode usage, error count.

## Acceptance Scenarios
1. Send three ordered chunks for a single utterance; server returns combined transcription.
2. Send request without `client_vad` flag; server runs fallback VAD and returns result.
3. Send corrupted chunk; server responds with error code `400` and logs incident.
4. Verify Prometheus metrics reflect correct VAD mode distribution.

## Edge Cases
- Out‑of‑order chunk arrival – server reorders based on sequence numbers.
- Missing chunks – server times out after 2 seconds and returns a partial result with warning.
- High‑frequency requests – rate limiting returns `429 Too Many Requests` after 100 req/s.

## Dependencies

- Monitoring stack (Prometheus/Grafana) configured in deployment.
